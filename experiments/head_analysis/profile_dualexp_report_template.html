0요약

dualexp_u40_em93p75(11.08B → 6.71B, −39.4%)는 무압축 대비 메모리 −8.8 GB(peak 21.5 → 13.3 GiB), latency는 릴리스 경로 1.06×, graphed fast path 1.36×(fast-vs-fast; stock 무압축 대비 1.56×). 메모리 감소는 네 arm 전부 bf16 가중치 산술과 0.09 GB 안에서 일치한다(KV 캐시 불변). 릴리스 경로의 이득은 prefill 하나(−27%, VLM 절단)에서 오고, decode/tok은 gather 경로 대가로 +2–6%, expert denoise는 가중치의 75%를 잘라내도 −2%(step-bound, G2 채택). 그런데 graphed 경로에서는 같은 expert 절단이 denoise 203.7 → 148.9 ms(−27%)로 단조롭게 보인다 — "expert MLP 폭은 latency에 무관"은 릴리스 경로 한정 진술이다. em87p5와 em93p75는 두 경로 모두 구별되지 않는다.

1질문과 사전 등록 예측

`slim_dualexp_u40_em93p75`가 무압축 Alpamayo-1.5-10B 대비 한 번의 추론(ViT → VLM prefill → CoC decode → expert denoise)에서 얼마나 빠르고 얼마나 적은 메모리를 쓰는가, 그리고 expert MLP 비율 사다리(75 → 87.5 → 93.75%)로 그 이득이 expert 가중치 바이트에 비례하는지. 선행(Blackwell, slim_int): expert 절단은 expert 단계를 거의 안 줄였고(378 → 377 ms) gather 경로 자체가 +87 ms였다. 예측 H1 메모리 = 산술 ±1 GB; H2 expert 단계 −15% 미만·사다리 무차이(step-bound); H3 prefill 0.70–0.85, 릴리스 e2e 1.0–1.15×; H4 fast path는 같은 경로 안에서 비교.

2설계

  • arm 5: 무압축(stock 경로) / dual_u40_v2(VLM 19/32 Q head + 60% MLP 절단, 8.42B) / dualexp_u40_em75(+ expert MLP 8256→2064, 7.05B) / em87p5(→1032, 6.82B) / em93p75(→516, 6.71B). expert Q head·KV·k/v_proj 불변. identity(무압축·gather 경로)는 제외 — 경로 대가는 선행 +87 ms를 참고치로.
  • 하드웨어: cvlab21 Ada 4–7(폐루프 드라이버와 같은 카드). 15 job을 빈 카드(<100 MiB)만 claim하는 4워커 풀로 동시 실행(launch_profile_arms.sh), 02:24–03:06 KST.
  • 릴리스 경로: profile_stages.py, CUDA 이벤트 모듈 훅으로 단계 타이밍, max_memory_allocated rollout/denoise peak, KV 캐시 MB. shard 2개(offset 0·13) × 12클립 + warmup. decode와 생성 루프 오버헤드는 baseline 중앙 CoC 길이 16토큰으로 정규화(프루닝 arm의 퇴화 rollout이 decode를 부풀리지 않도록).
  • fast path: bench_fastpipeline.py, 같은 클립에서 stock(release semantics)과 graphed(eager ViT+prefill → graphed decode 루프 → graphed expert denoise)를 나란히, 12클립. 이번에 전체 run peak 메모리 기록 추가.
  • 코드: 두 벤치의 REPO=/workspace/...를 __file__ 기준으로(호스트에서 처음 돌아감); 분석기는 옛 Blackwell 런으로 자체검증(analyze_slim의 1.03×·peak 15.4 G 재현).

4해석 (의견)

  1. 메모리는 완전히 예측 가능하다. 네 arm이 산술과 +0.09 GB로 일치하고 KV는 불변이다(k/v_proj·8×128 인터페이스를 안 건드리는 설계의 직접 결과). gather 경로의 활성화가 이득을 잠식한다는 H1 반증 조건은 성립하지 않았다.
  2. 릴리스 경로의 latency는 배치 1 런치 지배다. 파라미터 −39%가 시간 −6%로 바뀌는 이유는 단계별 표에 그대로 있다: prefill(큰 행렬곱, 3,000토큰)만 가중치에 비례해 줄고(−27%), decode(토큰당 1스텝)와 expert(64토큰 × 10스텝)는 커널 런치와 순차성이 지배해 가중치 바이트와 무관하다. em93p75/dual의 expert 비 0.985 [0.948,1.003]는 선행 slim_int의 378 → 377 ms를 Ada에서, 그리고 훨씬 큰 절단에서 재현한 것이다.
  3. 그러나 step-bound는 경로의 성질이지 모델의 성질이 아니다. CUDA graph로 런치를 걷어내면 같은 expert 절단이 denoise 203.7 → 160.0 → 153.8 → 148.9 ms로 단조롭게 나타나고(−27%), graphed decode도 27.3 → 19.4 ms/tok(−29%)로 VLM 절단을 드러낸다. 그래서 H4의 "graph 이득은 arm 무관" 가정은 틀렸다 — stock→fast 이득이 base 1.15×에서 em93p75 1.48×로 커진다. latency 수치는 반드시 경로 이름과 함께 인용해야 한다: 1.06×(릴리스)와 1.36×(graphed)는 같은 모델의 두 얼굴이다.
  4. 사다리의 끝은 의미가 없다. em87p5와 em93p75는 두 경로 모두 잡음 안이고(릴리스 1.079 vs 1.061×, fast 1.391 vs 1.362×), 메모리 차이 0.23 GB다. expert MLP 1032 → 516의 추가 절단은 latency·memory 어느 쪽도 사주지 않으므로, 그 선택은 성능(개루프·폐루프) 쪽 근거로만 정당화되어야 한다.
이 레포의 다른 결과와의 연결. "expert MLP 폭은 공짜"(2026-08-28, 개루프 minADE 기준)는 성능 진술이었고, 이번 결과는 그 폭이 비용 쪽에서도 릴리스 경로에서는 거의 아무것도 돌려주지 않는다는 뜻이다 — 배포 경로가 graphed일 때만 27%가 돌아온다. 반대로 VLM 절단(dual)은 prefill로 릴리스 경로에서도 확실히 돌아온다. 배포 목표가 latency라면 절단 예산은 VLM prefill과 graphed denoise에, 메모리라면 어느 축이든 산술대로다.

5한계

  • 배치 1, 단일 추론. 처리량(배치 > 1)에서는 expert의 가중치 재사용이 달라져 결론이 바뀔 수 있다.
  • identity arm이 없어 gather 경로 대가(선행 Blackwell +87 ms)를 이번 측정 안에서 분리하지 못했다. dual/base의 dec/tok +5.7%가 그 대가의 흔적이다.
  • 4 run 동시 실행(CPU·PCIe 공유). 선행과 같은 조건이라 arm 간 비교는 공정하지만 절대값은 단독 실행보다 보수적일 수 있다.
  • fast path의 peak는 두 경로와 graph 풀을 합친 run 전체 값이라 배포 시 fast path 단독 peak보다 크다.
