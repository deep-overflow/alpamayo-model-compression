# 개루프에 안전 축 하나: 예측 궤적 × 3D 장애물 박스

## 질문

개루프는 지금 minADE / minFDE만 본다. 둘 다 GT 궤적과의 거리이고, **무엇에 부딪히는지는
보지 않는다**. 폐루프에서 이 구분이 실제로 arm을 갈랐다 — 합산 250씬에서 `lp_r50`은 종합
점수가 `tyr_u40_r`보다 높은데 전체 충돌은 16.1% 대 9.7%로 나빴다. 점수가 못 보는 축이
방법을 갈라놓은 것이다.

개루프에도 같은 축이 있는가? 데이터셋에 3D 장애물 트랙이 있으므로 원리상 가능하다.

## 데이터 확인 (이미 한 것)

`labels/obstacle.offline` — 클립당 오토라벨 3D 트랙:

```
timestamp_us, track_id, center_x/y/z, size_x/y/z, orientation(quat),
label_class, reference_frame='rig', reference_frame_timestamp_us
```

클래스는 automobile 12만 / person 3.4만 / heavy_truck / bus / rider / trailer / stroller /
animal, 클립당 트랙 40개 수준. 소스 `scene:obstacles:autolabels:v2`.

자차 크기는 `calibration/vehicle_dimensions`에 클립별로 있다(`length` 4.872,
`width` 2.121, `rear_axle_to_bbox_center` 1.327 …). 로컬 7.3 MB, 전 청크 보유.

**이탈(offroad)은 불가능하다.** `features.csv` 전체에 차선·도로경계·주행가능영역 라벨이
없다. 개루프에서 "도로를 벗어났다"를 판정할 기준이 데이터셋에 존재하지 않는다.

## 두 개의 장애물

**1. 예측 궤적이 저장되지 않는다.** `run_baseline.py`는 `pred_k` (8, 64, 2)를 계산하고
ADE/FDE 스칼라만 남긴 뒤 버린다. **기존 실행에서는 이 지표를 만들 수 없다.** 어떤 설계를
택하든 재실행이 필요하다.

**2. 평가셋의 장애물 라벨이 로컬에 없다.**

| 세트 | obstacle 라벨 |
|---|---|
| `calib_100` | 96 / 100 |
| `test_500` | **0 / 500** |
| `indist_500` | **0 / 500** |
| `ood_val` | **0 / 262** |

캘리브레이션 청크만 받아져 있다(4.6 GB / 95청크). 평가셋은 청크 323·180·209개가 필요한데,
`build_cache.py`가 쓰는 클립 단위 스트리밍(`open_file(maybe_stream=True)`)이면 청크 통째
받기(~34 GB)보다 훨씬 싸다.

## 기하 — 좌표계가 이 작업의 전부다

장애물은 **각 행의 시각의 rig 프레임**에 있다(`reference_frame_timestamp_us == timestamp_us`).
`ego_future_xyz` / `ego_future_rot`은 **t0의 rig 프레임** 기준 미래 64 pose다. 따라서 시각
`t_i = t0 + 100ms·i`의 장애물을 t0 프레임으로 옮기는 변환이 곧 GT 미래 pose다:

```
c_t0 = R_i · c_rig(t_i) + p_i          # R_i = ego_future_rot[i], p_i = ego_future_xyz[i]
```

예측 궤적은 t0 프레임의 2D 경로 `p̂_i`이므로, 같은 프레임에서 자차 박스와 장애물 박스의
겹침을 본다. 자차 heading은 예측 경로의 접선(유한차분)으로 잡는다 — 모델이 heading을
따로 내지 않기 때문이고, footprint 판정에는 충분하다.

**GT가 검증한다.** GT 궤적을 같은 판정에 넣으면 충돌이 0에 가까워야 한다. 그렇지 않으면
프레임·시간정렬·박스 크기 중 하나가 틀린 것이다. 이것이 이 계획의 첫 게이트이고, GPU가
전혀 필요 없다.

## 단계와 게이트

### Phase 0 — 기하 검증 (GPU 0, calib_100, 이미 있는 라벨로)

`calib_100`의 96클립에서 **GT 궤적**으로 충돌 판정을 돌린다.

- **G0 통과**: GT 충돌률 < 2%. 자차가 자기 미래 경로를 따라가며 라벨된 장애물과 겹치지
  않는다는 뜻이고, 기하가 옳다는 증거다.
- **G0 실패**: 5% 이상이면 프레임 변환이나 시간 보간이 틀렸다. 원인을 찾기 전에는
  다음 단계로 가지 않는다.

오토라벨 오탐이 있으므로 0%를 요구하지 않는다. 실패 시 진단으로 남길 것: 충돌한
`label_class` 분포, 충돌 시각 분포, 겹침 깊이 분포.

### Phase 1 — 궤적 저장 + 라벨 확보

- `run_baseline.py`에 `--save-pred`를 추가해 `pred_k`를 per-clip 행에 넣는다.
  8×64×2 float32 = 4 KB/클립, 500클립이면 2 MB — 무시할 수 있다.
- 평가셋 3종의 obstacle 라벨을 클립 단위로 스트리밍해 받는다.

### Phase 2 — arm 재실행과 판정

`baseline`, `tyr_u40_r`, `tyrK`, `tyr_rd_a`, `tyr_rd_b`, `dual_u40_v2`, `dualr_u40`
7개 arm × 3세트. cvlab20 4카드 샤딩으로 arm당 53분 → **약 6 GPU-시간**.

- **G1 (지표가 살아 있는가)**: 무압축 baseline의 충돌률이 GT보다 유의하게 높아야 한다.
  아니라면 이 지표는 8샘플 중 어느 것도 장애물 근처로 가지 않는다는 뜻이고, 변별력이 없다.
- **G2 (새 정보인가)**: 충돌률과 minADE의 arm 간 Spearman |ρ| < 0.7. 그보다 높으면
  minADE를 다르게 쓴 것에 불과하다.
- **G3 (arm을 가르는가)**: 폐루프에서 갈렸던 쌍(`lp_r50` 대 `tyr_u40_r`처럼)이 개루프
  충돌에서도 갈리는지. 갈리면 개루프에 안전 축이 생긴 것이고, 안 갈리면 "폐루프에서만
  보이는 것"이라는 결론이 강해진다.

## 보고할 통계

샘플 8개에 대해 셋을 낸다 — 어느 하나만으로는 오해를 만든다.

| | 뜻 |
|---|---|
| `collide_any` | 8개 중 하나라도 충돌 (최악 사례) |
| `collide_frac` | 8개 중 충돌한 비율 (분포) |
| `collide_best` | minADE가 가장 낮은 샘플의 충돌 여부 (실제로 고를 궤적) |

여기에 `ttc_min`(최소 충돌여유시간)과 `min_dist`(최소 이격거리)를 연속 대리지표로 같이
낸다. 충돌은 드문 사건이라 n=500에서 검정력이 약할 것이 예상되기 때문이다 — 폐루프에서
`analyze_longitudinal.py`가 존재하는 이유와 같다.

## 무엇을 주장하지 않을 것인가

- **이것은 폐루프 충돌이 아니다.** 다른 차들은 우리 예측에 반응하지 않는다(로그 재생).
  실제로는 피했을 상황이 충돌로 세어진다. 절대 충돌률은 상한이지 추정치가 아니다.
- **오토라벨이다.** `scene:obstacles:autolabels:v2`이고 사람이 검수한 라벨이 아니다.
  arm 사이 비교(같은 라벨을 공유)에는 무해하지만 절대값은 라벨 품질에 종속된다.
- **heading은 유도값이다.** 경로 접선으로 잡으므로 저속·정지 구간에서 불안정하다.
  속도 0.5 m/s 미만 구간은 직전 heading을 유지한다.
