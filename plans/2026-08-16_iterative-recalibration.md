# 반복 재캘리브레이션 — 스테이지별 재측정이 원샷 컷을 이기는가

날짜: 2026-08-16 (KST) · 상태: 실행 (2026-08-18 승인 — 범위를 5개 기준 전부로 확장,
개루프 판정 지표를 minADE@6으로 변경) ·
선행: `plans/2026-08-15_importance-calibration.md` →
`reports/evaluation/2026-08-16_importance-calibration.html`

## 가설

1차 Taylor 스코어는 "지금의 네트워크"에서 잰 국소 미분인데, 39.86%를 한 번에 자르면
스코어를 잰 네트워크와 실제로 잘리는 네트워크가 크게 다르다. 캘리브레이션 진단이 그 간극을
직접 보였다:

- **G-CAL-C**: 실제 컷 규모의 그룹 손상이 단독 손상의 합에서 5~55배 이탈(sub-additive),
  그룹이 클수록 악화. 부분 컷 뒤의 네트워크는 보상으로 재배선되고, 원래 스코어는 그
  재배선을 모른다.
- **dual − traj < 0 (teacher-forced에서도)**: 추론 항이 궤적 Taylor의 동시-제거 사각지대를
  메우는 정규화자로 작동 — 사각지대가 실재한다는 end-to-end 증거.

**H1**: 같은 예산·같은 기준에서, 컷을 3스테이지로 나눠 스테이지마다 마스킹된 모델에서
스코어를 재측정하면 원샷보다 test_500 minADE@6이 낮다. 재측정은 앞선 컷 이후 하중을 새로
짊어진 유닛을 보호할 수 있고, 원샷은 그럴 수 없다.

**H2 (확장으로 추가, 탐색적)**: 원샷 대가가 큰 기준일수록 스테이징의 회복이 크다. 특히
단일 기준 arm(coc, j)의 붕괴가 스테이징으로 구제된다면, "결합이 필요하다"의 상당 부분이
"원샷 근사가 나빴다"로 재귀속된다.

## 설계: 1요인 = 스테이징, 5개 기준 전부

각 `slim_<crit>_u40_v2`에서 **스테이지 수만** 바꾼다 (crit ∈ {traj, coc, dual, jtraj, j}).
기준 구성(rank_norm + max), calib_100, uniform 할당, 최종 예산(레이어당 Q 13/32 ·
MLP 4898/12288 컷), expert/KV 미개입, 모델 리비전 7aba829 전부 동일.

```
스테이지 s의 누적 컷 수 (레이어당, floor(K·s/3 + 0.5)):
  Q   : 4 → 9 → 13        MLP : 1633 → 3265 → 4898

stage 1: 저장된 스코어 그대로 (importance_v2 / jlens_v2 — 무손상 모델 측정,
         원샷과 같은 출발점, 새 측정 없음)
stage 2·3: 누적 마스크를 적용한 모델에서 해당 기준의 스코어를 재측정
         → 생존 유닛 중 하위를 추가 컷
최종: make_slim --config <crit>_u40_it3 → slim_<crit>_u40_it3
```

기준별 재측정 내용 (스테이지당):

| criterion | 재측정 패스 | 비고 |
|---|---|---|
| traj / coc / dual | `run_importance --mask` 1회 (~1 h) | 한 패스가 두 목적 모두 산출 |
| j | `run_jlens --mask` 1회 (~8 h) | teacher refs 고정 → J 절반은 텍스트 드리프트 없음 |
| jtraj | importance + jlens 각 1회 | 두 절반 모두 재측정 |

- 마스크 hook이 게이트/통계 hook보다 먼저 설치되므로 마스킹된 유닛의 기울기·활성 통계는
  구조적으로 0 — 잘린 유닛이 순위에 재진입할 수 없다 (`run_imp_calib`에서 합성 검증됨).
- importance 절반의 CoC 텍스트는 각 스테이지 모델 자신의 rollout(자기일관적, 드리프트
  있음 — 스테이지별 rollout 퇴화율을 기록해 감시). jlens 절반은 저장된 teacher refs를
  teacher-force하므로 텍스트가 스테이지 간 고정이다 — 두 절반의 비대칭을 명시해 둔다.
- **스코어링은 Blackwell에서** (importance_v2·jlens_v2가 Blackwell 측정 — 스테이지 간
  아키텍처 혼입 방지). **평가는 Ada에서** (`baseline_ada` 페어드). GPU가 없을 때는
  `run_retry_host.sh`가 빈 카드를 기다린다 — 오케스트레이터 자체는 CPU 프로세스다.

### 구현 (완료분)

`run_importance.py --mask` / `run_jlens.py --mask` 추가, 오케스트레이터
`run_iter_prune.py`(CPU, 스테이지 루프 + 서브프로세스 런칭 + 재시작 시 완료 스테이지
재사용), `make_slim.py`에 `<crit>_u40_it3` 분기.

## 평가 프로토콜 — minADE@6

판정 지표는 **minADE@6 (best-of-6)** 이다. 실행은 k=8로 하되 per-sample 배열
(`ade_rollout_k`)을 저장하고 분석에서 앞 6개로 축소한다 — 궤적 시드가 `base + k`이므로
8-샘플 실행의 앞 6개는 6-샘플 실행이 뽑았을 것과 **정확히 동일**하다 (`analyze_arms --k`의
검증된 경로). 이렇게 하면 @8 판독도 함께 보존된다.

원샷 비교 행 중 per-sample 배열이 없는 것들은 재평가가 필요하다:

| arm | test 행의 ade_rollout_k | 조치 |
|---|---|---|
| traj / coc / j (08-12 평가) | 있음 | `--k 6` 축소만 |
| baseline_ada, dual, jtraj (08-09 평가) | 없음 | test_500 재평가 (k=8, Ada) |

## 사전 등록 게이트

- **R0 (구현 검증)**: 1스테이지 모드의 kept-set이 shipped `slim_<crit>_u40_v2`와 레이어
  36개 전부 비트 동일. — **2026-08-18 실측: 5/5 기준 모두 PASS.**
- **R1a (주, 방향)**: 기준별로 test_500 페어드 minADE@6, `it3 − oneshot`의 부트스트랩
  95% CI 상한 < 0 → 반복이 이득.
- **R1b (크기)**: 중앙값 ≤ −0.3 × (그 기준의 원샷 대가 중앙값 @6, vs baseline). 대가가
  기준마다 크게 다르므로(dual ~+0.05 vs j ~+0.6) 절대 임계가 아니라 상대 임계로 등록한다.
  R1a만 통과하고 R1b 미달이면 "방향은 맞지만 실용적 이득 미확정"으로 보고 (크기 임계를
  지표 바꿔치기 없이 분리 등록 — G1/C1의 교훈).
- **R2 (추론 축 안전)**: CoC 퇴화율 < 5%, nll_self 페어드 델타 병기. 원샷보다 높아지면
  R1과 무관하게 명시.
- **R3 (조작 점검)**: 최종 kept-set과 원샷의 중첩률(오케스트레이터가 자동 기록). > 95%면
  해당 기준의 R1 null은 "재측정이 선택을 바꾸지 않음"으로 귀속 — 효과 없음과 구분.
  중첩률은 성능 예측이 아니라 귀속 판정에만 쓴다 (VQA 보고서의 Jaccard 교훈).
- **R4 (탐색적, H2)**: 기준별 회복량(원샷 대가 − it3 대가)을 원샷 대가에 대해 정렬.
  사전 등록된 검정은 없고 다음 실험의 가설 생성용.
- **조건부 폐루프**: dual_it3가 R1a를 통과할 때만 alpasim 150씬. 개루프 부호가 폐루프에서
  뒤집힌 전례 2회 — R1a 통과를 폐루프 없이 헤드라인으로 쓰지 않는다.

## 한계 (미리 적어둠)

- **스케줄 미튜닝.** 3등분은 첫 시도값. 실패해도 "3등분이 안 됐다"이지 "반복이 안 된다"가
  아니다.
- **greedy 비최적.** 재측정은 국소 정보를 갱신할 뿐 조합 최적화가 아니다.
- **importance 절반의 목적함수 드리프트.** 스테이지별 rollout 텍스트가 달라진다
  (jlens 절반은 고정). 스테이지별 rollout 퇴화율을 기록해 감시한다.
- **calib_100 재사용.** 세 스테이지가 같은 클립을 본다. 선택이지 학습이 아니고 평가는
  서로소인 test_500.
- **아키텍처.** 스코어링은 Blackwell, 평가는 Ada로 갈라진다 — 스코어는 아키텍처 내
  일관성만 필요하고(스테이지 간), 평가는 baseline_ada와의 페어링만 필요하므로 서로
  독립이다. 다만 CoC rollout이 3–4% 클립에서 아키텍처에 따라 달라지므로 스코어링 카드
  종류를 config에 기록한다.
