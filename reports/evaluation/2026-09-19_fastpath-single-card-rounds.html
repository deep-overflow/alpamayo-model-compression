1목적과 사전 등록 예측

2026-09-16 측정의 fast-path 표는 arm당 12클립 × 1 run이고, 15 job을 빈 카드 풀(Ada 4–7)에 흩어 돌렸다. 그 표에서 em 사다리의 e2e 순서는 단조가 아니었고 "em87p5 ≈ em93p75, 차이는 잡음 안"이라고만 적었는데, 그 잡음의 크기를 잰 적이 없었다. 선행 데이터를 다시 읽으면(GPU 0) 오차의 위치가 보인다:

  • run 안의 클립 간 흔들림은 작다. 모든 클립의 prompt_len이 3086으로 같아 클립은 사실상 같은 계산의 반복이다 — fast denoise의 (max−min)/median 0.3–1.2%, fast prefill 1.4–3.7%.
  • 오차는 run(카드) 사이에 있다. dual / em75 / em87p5 / em93p75는 VLM이 비트 동일하므로 prefill이 같아야 하는데, 선행 중앙값은 505.6 / 505.5 / 499.7 / 525.0 ms였고 em93p75의 최솟값 520.7이 dual의 최댓값 508.1보다 컸다. 클립 표본 오차가 아니라 run 단위의 체계적 오프셋이다. e2e 비단조는 전부 여기서 나온다(denoise만 보면 그때도 단조).

그래서 클립 수만 늘려서는 이 오차가 줄지 않는다. 필요한 것은 카드 고정과 run 간 분산의 직접 추정이다. 예측: H1 같은 카드에서 VLM이 같은 네 arm의 prefill·dec/tok은 1% 안에서 일치한다(선행의 +4–5%는 사라진다). H2 fast denoise는 엄격히 단조이고 인접 세 쌍이 전부 분해된다. H3 H1이 서면 e2e도 단조가 된다; em87p5−em93p75(≈5 ms)의 분해 여부는 run 간 SD에 달렸다. H4 같은 arm 5 run의 e2e CV < 1%.

2설정

  • arm 5(선행과 동일): 무압축 nvidia/Alpamayo-1.5-10B / slim_dual_u40_v2(VLM −24.0%) / slim_dualexp_u40_em{75,87p5,93p75}(+ expert MLP 8256 → 2064 / 1032 / 516). 넷의 VLM 절반은 비트 동일.
  • 카드: cvlab21 Ada 4–7을 쓰던 em93p75 hard100 폐루프 체인이 완전히 끝난 뒤(13:06) 시작 — 4·6번이 먼저 비었지만 남은 폐루프 스택 둘이 CPU를 쓰는 동안은 기다렸다(eager prefill은 CPU 런치에 민감). 먼저 빈 4번 한 장을 claim해 25 run 전부를 고정, 매 run 직전 카드가 다시 빈 상태(< 100 MiB)인지 확인.
  • 순서: 5 × 5 순환 라틴 방진 — 라운드 r은 arm 목록을 r칸 회전. 각 arm이 각 위치를 정확히 한 번씩 차지해 발열·시간 드리프트가 arm과 교락되지 않는다.
  • run: bench_fastpipeline.py --num-clips 24 --clip-offset 0 --reserve-gb 8 --clip-cache outputs/clip_cache_fastpipe. 클립 0은 warmup(+graph capture), 1–24가 live; 앞 12개는 선행 run과 같은 클립(seed 42 순열). seed는 42 + ci로 라운드 간 동일 — CoC 길이가 라운드마다 같아(G0에서 확인) 라운드는 순수한 타이밍 반복이다. stock 경로도 같은 run에서 같이 잰다.
  • 동거 감시: run 동안 20 s마다 nvidia-smi --query-compute-apps 기록, 우리 외 프로세스가 찍히면 그 run을 무효화하고 재실행(발생 0건).
  • 집계: run 안은 24클립 중앙값(선행과 같은 정의, e2e = prefill + dec/tok × 16 + denoise). 라운드 간은 run 값 5개의 평균·SD·CV. arm 간은 같은 (라운드, 클립)끼리 짝지은 비의 중앙값, 계층 부트스트랩(라운드 재표집 → 라운드 안 클립 재표집, 10,000회) 95% CI — CI가 클립 잡음만이 아니라 run 간 항을 같이 싣는다.
  • 코드 변경: bench_fastpipeline.py에 --clip-cache(라이브 로드 25–42 s/클립을 디스크 캐시로; 로드는 타이밍 구간 밖)·--prefetch-only(GPU를 잡기 전에 CPU로 캐시 채움)·config.json에 gpu_index/clip_ids. 신규 launch_fastpath_rounds.sh, analyze_fastpath_rounds.py. 분석기는 선행 5 run을 가짜 2라운드로 물려 선행 표를 그대로 재현하고, 음성 대조가 선행 데이터의 em93p75 prefill +4.0–5.0%를 FAIL로 잡는 것을 확인한 뒤 썼다.
  • 비용: prefetch 11분(CPU만, 2.4 GB), 25 run 53분 38초(run당 ≈2.1분 — 계획의 5–6분 추정은 과대였다), Ada 1장.

4분석 (의견)

선행 표의 비단조는 카드 항이었다고 본다. 같은 카드에서 오프셋이 5.0% → 0.4%로 사라졌고, 사라진 위치가 예측한 그 단계(eager prefill)다. graphed 단계(dec/tok, denoise)는 선행에서도 arm 간 일치했으므로 "카드마다 eager 커널 런치 속도가 다르다"가 가장 단순한 설명이다 — 다만 이번 실험은 카드를 고정했을 뿐 카드 간 차이를 직접 재지는 않았으므로, 원인이 카드 자체인지 그때의 동시 실행(4 run 병렬의 CPU 경합)인지는 분리하지 못한다. 어느 쪽이든 처방은 같다: arm 비교는 한 카드에서 순차로.
  • G1의 MARGINAL은 실질적으로 통과로 읽는다. 미달 한 쌍은 오프셋 0.08%에 CI 상한 0.9999다. dec/tok의 CI 폭이 ±0.1%로 워낙 좁아 0.1% 미만의 차이도 1을 배제한다. 사전 등록한 규칙은 그대로 MARGINAL로 적되, 이 측정의 잡음 바닥은 prefill ≈ 0.4%, dec/tok ≈ 0.1%, denoise ≈ 0.1%로 정리할 수 있다. 다음부터 G1류 게이트는 "CI가 1을 포함"이 아니라 "오프셋이 실용 임계 미만"(동등성 검정)으로 등록하는 편이 맞다 — 측정이 정밀해질수록 떨어지는 게이트는 잘못 설계된 게이트다.
  • em87p5 ≈ em93p75는 이제 수치가 있는 진술이다. denoise에서는 둘이 갈린다(−1.85%, 2.9 ms). e2e에서 안 갈리는 것은 그 2.9 ms가 prefill의 run 간 SD(1.7–2.6 ms)와 같은 크기이기 때문이다. 즉 "차이가 없다"가 아니라 "0.2% 차이가 있고, 그것은 배포에서 의미 없는 크기"다. expert MLP를 87.5%에서 93.75%로 더 자르는 것은 latency로는 사는 것이 없고, 메모리 0.21 GiB만 산다.
  • expert MLP 절단의 수확 체감이 선명해졌다. dual 대비 denoise −21.5% / −24.7% / −26.1% — 첫 75% 절단이 이득의 82%를 가져가고, 나머지 18.75%p는 4.6%p를 더할 뿐이다. 남은 150 ms는 attention·launch·64토큰 고정비로 보이며 MLP 폭으로는 더 못 줄인다. 선행 표의 −27%(148.9 ms)는 다른 카드 값이었고 같은 카드에서는 −26.1%다.
  • 선행 리포트의 헤드라인은 거의 그대로 선다. "graphed fast path 1.36×"는 1.37×로, "stock 무압축 대비 1.56×"는 1.55×로 바뀐다. 바뀌는 것은 사다리 내부의 순서와 dual·em75·em87p5의 1–2% 과대평가다.
  • stock(eager) 경로는 이 박스에서 CV 1–3%다 — graphed의 10배. 릴리스 경로(profile_stages) 표의 em 사다리 차이(1.061–1.079×)는 이 크기의 잡음 안에 있을 가능성이 높다. 릴리스 경로에서 사다리 순서를 말하려면 같은 설계(한 카드 × 라운드)로 다시 재야 하고, 박스가 조용할 때 재야 한다. 이번 범위에서는 제외했다.

다음 단계 제안

  • latency를 인용할 때는 이 표(한 카드, 5라운드)를 쓰고 CV를 같이 적는다. 새 arm은 launch_fastpath_rounds.sh의 NAMES/CKPTS에 추가하면 같은 프로토콜로 돈다(run당 2분).
  • 릴리스 경로 재측정이 필요하면 profile_stages.py에 같은 --clip-cache를 붙여 같은 런처로 돌릴 수 있다(예상 1시간). 단 eager 경로는 CPU 부하에 민감하므로 다른 작업이 없는 시간대가 전제다.
  • prefill이 e2e의 52%(514 / 978 ms)로 가장 큰 단계이고 아직 eager다. 다음 latency 이득은 expert가 아니라 prefill의 graph화 / 커널 융합에 있다.

5한계

  • 한 카드(Ada 4번)의 결과다. 카드 간 절대값 차이는 이 실험이 제거한 대상이지 잰 대상이 아니다.
  • 배치 1 단일 추론의 latency이지 처리량이 아니다. 릴리스 경로는 범위 밖.
  • 라운드 5개는 run 간 SD의 추정으로는 작다(자유도 4). CV는 점추정과 라운드별 원값을 같이 보라.
  • 측정 동안 같은 박스에서 다른 작업이 CPU를 썼다(load 9–36). 라틴 방진이 arm과의 교락은 막지만 절대값은 조용한 박스보다 보수적일 수 있다. GPU는 공유하지 않았다(동거 0건).
  • peak는 두 경로와 graph 풀을 합친 run 전체 값이다(선행과 같은 정의).
