물리 제거 보고서의 전망이 실측 사실이 되었다. 단독으로는 latency를 거의 못 바꾸던 파라미터 절감(1.07×)이 CUDA graph로 dispatch를 상각하자 1.28× → 1.62×의 증분(1.27×)으로 잠금 해제됐다 — graph 단독 이득(1.28×)과 pruning 단독 이득(1.07×)의 곱(1.37×)보다도 크다. dispatch floor가 가중치 절감을 숨기고 있었다는 진단의 직접 증명이며, decode/tok에서 가장 선명하다: 비압축 24.4 vs slim 18.4ms (−25%, 가중치 −32%에 근접 비례).

1.방법 — 두 개의 graph

  • Expert denoise (A1): release 경로는 매 flow-matching step마다 공유 cache에 64 token을 append→crop한다. StaticPrefixCache(update가 저장 없이 cat만 반환)로 step을 순수 함수화하고, prefix K/V를 128-배수 버킷으로 패딩해 수동 torch.cuda.CUDAGraph로 캡처(버킷당 1회, ~0.4s). 패딩은 기존 4D mask가 [offset, kv−64) 구간을 −inf 처리하므로 구성상 정확.
  • CoC decode (A2): 고정 용량(3,456) StaticCache + 수동 샘플링 루프. 현재 길이가 shape이 아니라 데이터(cache_position 인덱스 + additive mask)라 캡처 1회(~0.9s)를 모든 clip·step이 공유. Qwen3VL 래퍼는 텐서 값 분기가 있어 language_model을 직접 호출하고 mrope 위치를 텐서 연산으로 계산. 샘플링(temperature/top-p + traj-vocab 마스킹)은 replay 사이 Python에서 수행.
  • 파이프라인: ViT+prefill(eager, compute-bound) → graphed decode → EOS step 1회(release 프로토콜과 cache 일치) → static 버퍼에서 prefix 구성 → graphed denoise. slim 모델은 gather forward(kv_head_index)가 그대로 캡처에 포함된다.
  • 제약: 컨테이너에 python3.12-dev 헤더가 없어 inductor(torch.compile)는 불가 — 수동 캡처는 kernel fusion 없이 launch 상각만 하므로, 이미지에 헤더를 추가하면 여지가 더 있다. 실행 시 PYTORCH_CUDA_ALLOC_CONF="" 필요(expandable_segments가 캡처와 충돌).

2.2 stage 세부

  • decode: graph로 35.3 → 24.4ms/tok(−31%), 거기서 pruning이 24.4 → 18.4(−25%, 가중치 −32% 대비 실현율 ~78%). 비graph에서는 같은 pruning이 −3%였다.
  • expert denoise: 440 → 217(graph, 2.0×) → 194(pruning 추가, −10%). Ada 단독 벤치에서는 2.36×.
  • ViT+prefill: fast 경로가 +90ms 느리다 — StaticCache prefill(고정 용량 mask 생성 + index_copy 쓰기) 오버헤드. 최적화 여지(예: DynamicCache prefill 후 버퍼 복사)로 남긴다.
  • 캡처 비용: decode ~0.9s ×1, denoise ~0.4s/버킷 — 전부 일회성, 서빙 시나리오에서 무시 가능.

3.분석 (해석)

  • 왜 곱보다 큰가 (1.28 × 1.07 = 1.37 < 1.62). stock에서 pruning 이득의 상한은 dispatch floor에 막혀 있었다(가중치를 지워도 launch 수 불변). graph가 floor를 걷어내자 decode·denoise가 bandwidth-bound로 복원되었고, 그 체제에서는 시간이 가중치 바이트에 비례하므로 pruning의 진짜 이득(1.27× 증분)이 드러났다. 두 최적화는 서로 다른 병목을 제거하므로 순서가 아니라 조합이 본질이다.
  • 남은 하한. slim decode 18.4ms/tok의 구성: 가중치 읽기 ~11ms + cap-길이 attention/KV 확장 ~5ms + glue ~2ms. 확장 제거(paged/GQA-native kernel)와 fusion(inductor)이 다음 여지다.
  • traj 전용 배포의 추가 레버. slim integrated는 여전히 퇴화 CoC를 평균 ~110 token 생성한다(정규화로 보정했지만 실제 배포에서는 실비용). CoC 생성 자체를 생략하면(prefill 직후 <|traj_future_start|> 강제) e2e ~600ms대 — ~2.3× 사정권이며, “expert가 cache의 어느 부분을 쓰는가”라는 연구 질문과 겹치는 다음 실험이다.
  • 품질은 그대로다. 두 graph 모두 수학이 동일한 경로의 재배치(cache 불변 denoise, static-KV decode)라 동등성 편차는 기존에 확정한 bf16 노이즈 플로어 안이다. 마스킹→물리 제거→graph 실행까지, P1–P3의 품질 결론은 전 구간에서 유효하다.
