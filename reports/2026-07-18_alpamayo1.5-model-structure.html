3.Action expert 36 layers, ~63.3M/layer

Built in code from a deepcopy of the VLM text_config with overrides {hidden_size: 2048, num_attention_heads: 16, head_dim: 128, intermediate_size: 8256}. Everything else is inherited from the VLM text config: 36 layers, 8 KV heads, head_dim 128. embed_tokens is deleted (inputs come from action_in_proj); has a final norm but no LM head. The expert is already a “width-pruned” sibling of the VLM decoder (hidden 4096→2048, Q heads 32→16, intermediate 12288→8256) with the KV geometry kept identical (8 KV heads × 128) — this is what makes VLM-KV-cache reuse possible (see §5).

4.Vision tower 27 blocks, ~15.2M/block

ViT: hidden 1152, 16 heads, intermediate 4304 (GELU-tanh), patch 16×16×(2 temporal), with biases.

  • patch_embed.proj [1152, 3, 2, 16, 16], pos_embed [2304, 1152]
  • Per block: fused attn.qkv [3456, 1152], attn.proj [1152, 1152], mlp.linear_fc1/fc2 (1152↔4304), LayerNorms with bias
  • merger + 3 deepstack_merger_list (taps after blocks 8/16/24): each ≈40M, spatial 2×2 merge (1152×4=4608 → 4096)
  • DeepStack: 3 intermediate feature maps are injected into early LLM layers (Qwen3-VL design)

5.Inference dataflow and the VLM↔expert coupling critical for pruning

Two-stage pipeline in Alpamayo1_5.sample_trajectories_from_data_with_vlm_rollout:

4 cams × 4 frames + 48 ego-history traj tokens → VLM autoregressive CoC rollout (≤256 tokens) → KV cache (prompt + CoC) → Expert flow-matching ×10 Euler steps, 64 tokens → Unicycle integration → 64 waypoints (6.4s @ 10Hz)
  1. VLM rollout: multi-camera frames + ego-history trajectory tokens (48 tokens, discrete tokenizer with 3,000 bins/dim) are fused into the prompt. vlm.generate autoregressively samples Chain-of-Causation text, stopping at <|traj_future_start|>. Discrete traj tokens are masked out of the logits (ExpertLogitsProcessor).
  2. Expert denoising: the expert runs flow matching (Euler, default num_inference_steps=10) over 64 diffusion tokens (one per waypoint, action dim 2 = accel/curvature). Each step: action_in_proj(x_t, t) → 64 embeddings → expert(inputs_embeds=..., past_key_values=prompt_cache) → action_out_proj → vector field. Actions are integrated by a unicycle model into 64 xyz+rot waypoints.
The expert consumes the VLM’s KV cache directly (past_key_values=prompt_cache, alpamayo1_5.py:346–349). Expert layer i attends over VLM layer i’s cached K/V of the whole prompt+CoC sequence, plus its own 64 diffusion tokens (non-causal self-attention among them, expert_non_causal_attention=true). This works only because:
  • expert depth (36) == VLM depth (36), 1:1 layer correspondence
  • expert KV projection dims (8 KV heads × head_dim 128 = 1024) == VLM KV dims
  • expert Q head_dim (128) == VLM head_dim, sharing M-RoPE position encoding (3D position ids)

6.Implications for pruning opinion

  • Layer pruning the VLM text stack is not free: removing VLM layer i removes the KV cache entry expert layer i reads. Options: (a) prune (VLM layer i, expert layer i) pairs jointly, (b) prune only expert layers (keep all VLM caches, skip expert consumption of pruned indices), (c) remap expert layers to surviving VLM caches. Any of these needs the layer-importance analysis to score the pair, not the VLM layer alone.
  • Width pruning inside a layer: Q heads and MLP intermediate channels of both stacks are independently prunable (per-layer, no cross-model constraint). KV heads / head_dim are shared geometry between VLM and expert — pruning them must be done consistently in both, and interacts with M-RoPE section layout.
  • Biggest single levers by size: VLM MLPs (5.4B), VLM attention (1.5B), expert MLPs (1.8B), embed_tokens+lm_head (1.3B, untied — vocab is 155,697 but only ~152k text tokens + traj/special tokens are ever used; traj tokens are masked during CoC generation).
  • Latency profile differs per stage: CoC generation is autoregressive over the 36-layer/4096-hidden VLM (memory-bandwidth bound, ~256 steps); the expert runs only 10 denoising forward passes over 64 tokens (but each attends to the full prompt-length cache). So VLM pruning helps latency far more; expert pruning mainly saves params/memory.
  • Next step per plan: attention-map / activation analysis (e.g., which VLM layers’ caches the expert actually attends to, per-layer angular distance between hidden states) to pick pruning candidates.

7.Repo note

The working repo alpamayo-model-compression is a fork of Alpamayo 1 (R1) code (alpamayo_r1 package, nvidia/Alpamayo-R1-10B weights — not cached locally). The cached weights and specified venv are Alpamayo 1.5 (/workspace/alpamayo1.5, alpamayo1_5 package). The two codebases are structurally near-identical (1.5 adds camera-id/frame-num conditioning, nav utils, minor refactors). This analysis targets Alpamayo-1.5-10B since those are the weights available locally.
